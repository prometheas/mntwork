# Nix image and artifact reuse: primary-source constraints

Research date and access date: 2026-08-07. Sources are current official Nix/Nixpkgs, direnv, nix-direnv, and OCI documentation or source. This note selects a logical ownership and trust model; runtime-specific mount, network, and performance feasibility remains for the macOS isolation spike.

## Facts that must shape the model

### Reproducible, versioned image

- A flake lock file maps normally unlocked inputs to locked input specifications, including revisions and NAR hashes. The image expression, Nixpkgs revision, Nix version, `direnv`, `nix-direnv`, shell/init utilities, certificates, and supported target systems can therefore live in one committed flake whose lock file is the build input. Updating any of them is an explicit lock-file/image release rather than startup-time installation. Sources: [Nix flake lock files](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-flake#lock-files), [Nix flake lock command](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-flake-lock).
- `dockerTools.buildLayeredImage` builds an image from declared Nix store contents and their closure, while `streamLayeredImage` streams the result without first materializing the tarball; image configuration is declared as part of the derivation. A scratch-style image can therefore contain only its declared runtime closure rather than inheriting a mutable general-purpose distribution. Source: [Nixpkgs `dockerTools`](https://nixos.org/manual/nixpkgs/stable/#sec-pkgs-dockerTools).
- OCI descriptors identify content by an algorithm-prefixed digest calculated from its bytes, and consumers are expected to verify untrusted content against that digest before use. A tag is a release/discovery label; the runtime contract should resolve it to, persist, and launch an OCI manifest digest. Sources: [OCI descriptor digest calculation](https://github.com/opencontainers/image-spec/blob/main/descriptor.md#digest-calculations), [OCI descriptor verification](https://github.com/opencontainers/image-spec/blob/main/descriptor.md#verification), [OCI image manifest](https://github.com/opencontainers/image-spec/blob/main/manifest.md).
- The official Nix Dockerfile downloads a selected Nix release, creates build users, configures Nix, installs into `/nix`, collects old generations, optimizes the store, and verifies store contents. It is useful evidence about required runtime setup, but its mutable branch and build argument are not an immutable mntwork release identity. Source: [NixOS Dockerfile](https://github.com/NixOS/docker/blob/master/Dockerfile).

**Model consequence:** publish one image per supported platform from a committed flake. Give each release a human version containing the mntwork image schema/release, but make `(platform, manifest digest)` authoritative. Keep project toolchains out of the base image; project flakes provide them. Record image digest and flake-lock hash in Sandbox observed state. Never install or update Nix tooling while starting a Workspace.

### Flake and worktree evaluation

- Flakes use `flake.lock` to make input revisions reproducible. `nix-direnv`'s `use flake` integration watches `.envrc`, `flake.nix`, `flake.lock`, and `devshell.toml` when present, then caches the evaluated shell environment for faster later loads. Sources: [Nix lock files](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-flake#lock-files), [nix-direnv tracked files](https://github.com/nix-community/nix-direnv/blob/master/README.md#tracked-files), [nix-direnv overview](https://github.com/nix-community/nix-direnv/blob/master/README.md).
- By default, nix-direnv falls back to a previously working dev shell when a changed one fails evaluation. `nix_direnv_disallow_fallback` disables that behavior. Silent fallback would make an interactive shell disagree with the checked-out worktree, so mntwork's managed integration should disable fallback and surface the evaluation failure. Source: [nix-direnv disabling dev-shell fallback](https://github.com/nix-community/nix-direnv/blob/master/README.md#disabling-devshell-fallback).
- nix-direnv retains shell build dependencies with GC roots and keeps per-project profiles and input links beneath direnv's layout directory. Those mutable accelerators are Workspace state, not image content or Workspace identity. Sources: [nix-direnv overview and GC-root behavior](https://github.com/nix-community/nix-direnv/blob/master/README.md), [nix-direnv `direnvrc` profile and GC-root implementation](https://github.com/nix-community/nix-direnv/blob/master/direnvrc).

**Model consequence:** the base image owns a pinned nix-direnv integration; each Worktree Context owns its checked-out `flake.nix`, `flake.lock`, and `.envrc`; each Workspace owns mutable direnv layout/profile state. Preparation evaluates the worktree exactly as mounted and fails closed. No cached shell may substitute for the current worktree after evaluation failure.

### `direnv` authorization for mounted worktrees

- direnv finds `.envrc`/`.env` files in the current or parent directories, checks authorization, and blocks a new or modified file until it is explicitly allowed. The file is shell code, so authorization is a code-execution trust decision rather than a performance switch. Source: [direnv manual](https://direnv.net/man/direnv.1.html).
- `direnv allow [PATH_TO_RC]` resolves the selected file, hashes its content, and records the authorization under direnv's allow directory. The manual locates those records under `$XDG_DATA_HOME/direnv/allow`; the implementation resolves the path supplied to `allow` and hashes the file before recording it. Sources: [direnv files and environment](https://direnv.net/man/direnv.1.html#FILES), [direnv `allow` implementation](https://github.com/direnv/direnv/blob/master/internal/cmd/cmd_allow.go).
- Authorization is mutable user/workspace state. Baking allow records into an image would mix trust decisions with image identity and cannot authorize later absolute mount paths safely. This is a design inference from direnv's per-file authorization record and XDG data location. Sources: [direnv manual](https://direnv.net/man/direnv.1.html), [direnv `allow` implementation](https://github.com/direnv/direnv/blob/master/internal/cmd/cmd_allow.go).

**Model consequence:** explicit Workspace preparation is the trust boundary. After all mounts are validated, mntwork runs `direnv allow` inside the Sandbox for each configured worktree's exact mounted `.envrc`, before first shell evaluation. Store `$XDG_DATA_HOME/direnv` under Workspace-owned state so authorization survives shell detach/re-entry but does not cross Workspace isolation. A changed `.envrc` has a new hash and must block until a later explicit prepare/authorize action; shell entry must never auto-allow an unexpected change. Report each worktree as absent, authorized-current, changed-and-blocked, or evaluation-failed.

### Isolated stores and shared artifact reuse

- A Nix local store is accessed directly in a filesystem root and includes the store plus Nix state. A local binary cache is a different store type: `file://PATH` is a read/write directory containing the binary-cache format. `nix copy` transfers closures between stores and binary caches. Sources: [Nix local store](https://nix.dev/manual/nix/latest/store/types/local-store), [Nix local binary cache store](https://nix.dev/manual/nix/latest/store/types/local-binary-cache-store), [`nix copy`](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-copy).
- The binary-cache protocol exposes `nix-cache-info`, per-object `.narinfo` metadata, and compressed NAR payloads. `.narinfo` metadata identifies the store path, payload URL, NAR hash and size, references, and signatures. This format is suitable for read-only HTTP(S) serving as well as a local filesystem cache. Sources: [Nix binary-cache protocol](https://nix.dev/manual/nix/latest/protocols/binary-cache/), [Nix HTTP binary cache store](https://nix.dev/manual/nix/latest/store/types/http-binary-cache-store).
- `nix store verify` checks that store contents match their recorded NAR hash and that paths are trusted by a trusted signature, content addressing, or a local build. `nix store sign` adds signatures using a secret key, while `trusted-public-keys` and `require-sigs` control substitution trust. Sources: [`nix store verify`](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-store-verify), [`nix store sign`](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-store-sign), [Nix `require-sigs`](https://nix.dev/manual/nix/latest/command-ref/conf-file#conf-require-sigs), [Nix `trusted-public-keys`](https://nix.dev/manual/nix/latest/command-ref/conf-file#conf-trusted-public-keys).
- GC roots keep a local-store path and its dependencies alive while the root exists. They protect a Workspace's local store; they are not a retention contract for flat binary-cache NAR files. Source: [Nix garbage-collector roots](https://nix.dev/manual/nix/latest/package-management/garbage-collector-roots).
- The local-binary-cache manual promises read and write access through a filesystem path, but does not define cross-VM filesystem locking, crash recovery, or many-writer ownership. Runtime-shared read/write mounts would also grant every Workspace authority to alter cache metadata. The safe portable contract is therefore one owner for publication and many read-only consumers, not concurrent direct writers. Source for the documented interface boundary: [Nix local binary cache store](https://nix.dev/manual/nix/latest/store/types/local-binary-cache-store).

**Model consequence:** every Workspace gets its own writable Nix local store, exposed only to that Workspace's Sandbox and persisted independently from Sandbox generations by default. It does not mount the host `/nix`, a host Nix daemon socket, another Workspace's store, or a shared writable Nix store. Cross-Workspace reuse comes from an optional mntwork-owned binary-cache service or cache snapshot, exposed read-only over HTTP(S) or a read-only mount and configured as one substituter.

One cache publisher owns cache mutation, signing, verification, temporary-file cleanup, retention, and serialization. Workspaces receive only cache endpoint/read mount plus public verification keys; private signing keys never enter a Workspace. Publication must come from a trusted build/publisher path, because a valid cache signature attests publisher trust, not independent reproducibility of arbitrary Workspace output. Direct Workspace upload is out of the trusted-cache contract unless a later protocol adds authentication, admission, and trusted rebuild policy.

### Cache misses, corruption, GC, and external-drive failure

- Nix can copy closures from a cache and can repair missing or corrupted local-store files during evaluation/build with `--repair`. Store verification checks both recorded contents and trust. These are recovery primitives, not permission to treat a shared cache as authoritative state. Sources: [`nix copy`](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-copy), [`nix store verify`](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-store-verify).
- Substituters are configured cache locations, while the normal build path remains available when a required output is not present in a substituter; `--offline` is the explicit mode that disables substituters/network fetch behavior. Therefore cache absence must remain a performance event, not an identity or correctness error. Sources: [Nix `substituters`](https://nix.dev/manual/nix/latest/command-ref/conf-file#conf-substituters), [Nix common `--offline` option](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix#opt-offline), [`nix copy`](https://nix.dev/manual/nix/latest/command-ref/new-cli/nix3-copy).
- A local store's `root` is an absolute prefix for the store and related directories. A local binary cache's `file://` path can likewise live anywhere in the mounted filesystem. This permits data-root relocation without changing logical OCI image identity or flake inputs. Sources: [Nix local-store root](https://nix.dev/manual/nix/latest/store/types/local-store), [Nix local binary cache path](https://nix.dev/manual/nix/latest/store/types/local-binary-cache-store).

**Model consequence:** cache lookup returns hit, miss, unavailable, untrusted, or corrupt. Hit imports a verified closure into the private store. Miss continues to later trusted substituters and then normal evaluation/build. Unavailable, untrusted, or corrupt entries are quarantined/rejected and surfaced diagnostically; they never change Workspace or Sandbox identity. Do not default managed shells to offline mode.

The configured data root may place cache service data, per-Workspace stores, direnv state, and other mntwork-owned state on an external drive. Drivers mount each selected host path at a stable in-sandbox target; persisted metadata keeps a logical data-root identifier and observed backing-device facts, never the cache contents or a transient mount enumeration as identity. Preflight must reject an absent, wrong, read-only, or permission-incompatible drive before creating fallback directories. If the drive disappears while running, cache reads become unavailable; work needing a missing store or state fails explicitly and must not redirect to the host's same-looking path. Reattachment requires ownership/format validation before service restart.

## Selected ownership and identity model

1. **Image:** flake-built, closure-minimal, platform-specific OCI image. Version for humans; manifest digest for execution and reconciliation.
2. **Workspace private state:** direnv authorization/layout state and any declared persistent state. Never part of image or shared cache identity.
3. **Workspace local store:** writable and isolated. It is authoritative for currently installed/evaluated paths, persists across Sandbox generations by default, and is removed only by explicit Workspace pruning or removal policy.
4. **Shared artifact cache:** optional, signed, read-only to Workspaces, single-publisher, independently prunable. It accelerates private-store population but is not required for correct evaluation/build.
5. **Immutable identity:** Workspace identity comes from Workspace definition; Worktree Context identity from its configured repository/worktree membership; Sandbox identity from Workspace plus driver-owned resource ID and pinned image digest. Flake lock hashes and effective store paths are observed inputs/state. Cache location, cache generation, hit/miss result, GC epoch, and external-drive device name are never identity inputs.
6. **Failure contract:** cache miss or outage degrades speed; signature/hash failure rejects that artifact; private-store corruption triggers verify/repair or rebuild; external-state loss blocks writes that need it. None silently selects a different image, stale nix-direnv environment, host store, or alternate data root.

## Research boundary

Official sources establish image, flake, authorization, store, cache, signature, and GC mechanics. They do not prove that Docker Sandboxes, nested Podman, or Apple's `container` can expose one cache endpoint or external-drive path with acceptable isolation and performance. They also do not specify a portable many-writer filesystem cache protocol. Those points require the separate runtime-isolation spike; this model deliberately needs only private writable stores plus optional read-only cache consumption.
