# Runtime Driver interface: primary-source constraints

Research date and access date: 2026-08-05. Sources are current official Docker, Podman, and Apple documentation or source documentation. This note constrains a capability contract; it does not select or prove a macOS isolation strategy.

## Facts that must shape the contract

### Preflight and capability reporting

- Docker exposes versioned Engine API operations plus daemon `/_ping`, `/version`, and `/info` data. API-version mismatch is a protocol error, while daemon information includes host/runtime facts. Podman `info` exposes host architecture, kernel, cgroups, OCI runtime, networking, storage, and version data. Apple `container system status` and `container system version` expose service state and whether the API server answers its health check. A driver can therefore probe installation, reachability, version compatibility, runtime host, and service health before creation rather than inferring support from executable presence. Sources: [Docker Engine API](https://docs.docker.com/reference/api/engine/), [Podman info](https://docs.podman.io/en/latest/markdown/podman-info.1.html), [Apple command reference](https://github.com/apple/container/blob/main/docs/command-reference.md#container-system-status).
- Host and runtime host are not always the same machine. Docker bind mounts resolve on the daemon host, not the client; Docker Desktop mediates host paths into its Linux VM. Podman remote defaults generally come from the server's `containers.conf`. Apple `container` currently requires Apple silicon. Compatibility reports therefore need separate CLI-host and runtime-host facts plus explicit reasons for unsupported mount, network, socket, or workload-engine capabilities. Sources: [Docker bind-mount constraints](https://docs.docker.com/engine/storage/bind-mounts/#considerations-and-constraints), [Podman create](https://docs.podman.io/en/latest/markdown/podman-create.1.html), [Apple container README](https://github.com/apple/container#requirements).
- Capability support cannot be one boolean. Examples vary by kernel, privilege mode, network mode, API version, and runtime configuration: Docker recursive read-only bind mounts require Linux 5.12 or later; Podman port publishing is limited to supported network namespaces/modes; Apple exposes some features as experimental or hardware/OS-dependent. Report each requested feature as supported, unsupported, or degraded, with machine-readable reason and backend evidence. Sources: [Docker recursive mounts](https://docs.docker.com/engine/storage/bind-mounts/#recursive-mounts), [Podman publish](https://docs.podman.io/en/latest/markdown/podman-create.1.html#publish-p-iphostportcontainerportprotocol), [Apple command reference](https://github.com/apple/container/blob/main/docs/command-reference.md).

### Lifecycle, identity, and reconciliation

- Docker's Engine API has distinct create, inspect, start, attach/exec, stop, kill, and delete operations and standard HTTP status/error bodies. Podman likewise creates without starting, prints a container ID, and begins in `created` state. Apple distinguishes start, exec, graceful stop, immediate kill, and delete; its stop sends `SIGTERM` by default and escalates to `SIGKILL` after a timeout, while kill defaults to `KILL`. The interface must preserve distinct graceful-stop, forced-stop, and destroy intents instead of collapsing them. Sources: [Docker Engine API container operations](https://docs.docker.com/reference/api/engine/version/v1.52/#tag/Container), [Podman create](https://docs.podman.io/en/latest/markdown/podman-create.1.html), [Apple lifecycle commands](https://github.com/apple/container/blob/main/docs/command-reference.md#container-stop).
- Attachment is stateful. Docker creates an exec instance and starts/attaches it separately; Podman and Apple exec target running containers, and Apple start can optionally attach standard streams. The contract needs a typed attach request (shell versus argv, interactive/TTY, stdin, environment, user, workdir) and must return an explicit not-running or unsupported-attachment error. Sources: [Docker Engine API exec operations](https://docs.docker.com/reference/api/engine/version/v1.52/#tag/Exec), [Podman exec](https://docs.podman.io/en/latest/markdown/podman-exec.1.html), [Apple exec](https://github.com/apple/container/blob/main/docs/command-reference.md#container-exec).
- Names, IDs, labels, states, and health are backend-owned data. Docker and Podman expose inspect/list state and labels; Apple list supports structured output and accepts names as container IDs. Persist an opaque driver identifier plus mntwork ownership labels/metadata, then reconcile by list/inspect. Normalize at least absent, creating, created/stopped, starting, running, stopping, unhealthy, deleting, and unknown rather than treating a stale local record as authoritative. Sources: [Docker Engine API inspect/list](https://docs.docker.com/reference/api/engine/version/v1.52/#tag/Container), [Podman inspect](https://docs.podman.io/en/latest/markdown/podman-inspect.1.html), [Apple list](https://github.com/apple/container/blob/main/docs/command-reference.md#container-list-ls).
- Forced deletion differs from orderly cleanup: Docker force-delete kills a running container; Podman and Apple expose force removal; auto-remove may erase state after exit. No backend API alone proves that all driver-created networks, storage, forwarding, sockets, or metadata were removed. `destroy` therefore needs a declared cleanup scope, post-delete verification, residual-resource reporting, and repeatable reconciliation for partial failure. Sources: [Docker Engine API delete](https://docs.docker.com/reference/api/engine/version/v1.52/#tag/Container/operation/ContainerDelete), [Podman rm](https://docs.podman.io/en/latest/markdown/podman-rm.1.html), [Apple delete](https://github.com/apple/container/blob/main/docs/command-reference.md#container-delete-rm).

### Mounts and persistent data

- Bind mounts are explicit source/destination mappings. Docker requires an absolute destination; `--mount` errors when its source is absent unless source creation is requested. Bind mounts default writable, obscure pre-existing destination content, and are tied to the runtime host's directory layout. Podman and Apple likewise accept explicit mount source, target, and read-only settings. Model mounts as an ordered collection, not one workspace field. This accommodates multiple Worktree Contexts, every linked common Git directory, Workspace Root, and configurable data roots, each with independently validated source, identical absolute target where required, access mode, and propagation requirements. Sources: [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/), [Podman mount option](https://docs.podman.io/en/latest/markdown/podman-create.1.html#mount-typetype-type-specific-option), [Apple mount option](https://github.com/apple/container/blob/main/docs/command-reference.md#container-create).
- Exact-path preservation is a capability, not a portable assumption. A driver must preflight every source and target pair on the actual runtime host and reject unsupported translation before side effects. It must not silently omit an extra worktree/common-Git-dir mount or substitute one aggregate mount, because no cited runtime discovers mntwork's linked Git topology for it. Docker's documented remote-daemon behavior makes this distinction especially important. Source: [Docker bind-mount constraints](https://docs.docker.com/engine/storage/bind-mounts/#considerations-and-constraints).
- Runtime-internal storage and mntwork-mounted data are separate concerns. Docker's daemon `data-root` relocates much daemon state, but newer containerd-backed image/snapshot data may require separate containerd configuration, and two daemons must not share one data directory. A workload-engine request therefore needs explicit requested data mounts plus reported effective engine storage roots; “configured data root” cannot imply all backend bytes live beneath one path. Source: [Docker daemon data directory](https://docs.docker.com/engine/daemon/#daemon-data-directory).

### Workload engine, ports, routes, and channels

- Docker and Podman expose APIs through Unix sockets or protected remote transports, but neither socket is a narrow authority: Docker client credentials can issue any daemon instruction and may grant root-level control; Podman's API grants all Podman functionality and arbitrary code execution as the service user. Socket pass-through must therefore be an explicit privileged channel with source, target, access/transport, ownership, and risk metadata—not an incidental mount or generic “Docker-compatible” flag. Sources: [Protect the Docker daemon socket](https://docs.docker.com/engine/security/protect-access/), [Podman system service security](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html#security).
- Podman's service exposes both Docker-compatible and Libpod APIs, but compatibility does not establish identical behavior. Availability of an internal Docker or Podman workload engine should be reported independently from sandbox-runtime availability: engine kind, API/version, endpoint transport, daemon/rootless mode, health, storage root, and whether lifecycle is driver-managed. Do not encode a nested-daemon, host-socket, or VM-service strategy into the common contract. Source: [Podman system service](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html).
- Docker and Podman port publishing includes container port, host port (possibly dynamically assigned), host bind address, and protocol; reachability also depends on network/gateway mode and routing. Apple accepts `[host-ip:]host-port:container-port[/protocol]`. Keep requested port publications and higher-level route inputs distinct: drivers return effective bindings/endpoints, while a later route manager consumes route intent. Sources: [Docker port publishing](https://docs.docker.com/engine/network/port-publishing/), [Podman publish](https://docs.podman.io/en/latest/markdown/podman-create.1.html#publish-p-iphostportcontainerportprotocol), [Apple publish option](https://github.com/apple/container/blob/main/docs/command-reference.md#container-create).
- Apple exposes dedicated socket publication and SSH-agent forwarding alongside general mounts; Docker documents tmpfs as suitable for ephemeral sensitive material. These support a generic narrow-channel shape (named purpose, direction, source/broker endpoint, target, lifetime, read-only/ephemeral policy) for agents and future credential brokers. They do not justify resolving credential acquisition or 1Password brokering in this ticket. Sources: [Apple create options](https://github.com/apple/container/blob/main/docs/command-reference.md#container-create), [Docker storage mounts](https://docs.docker.com/engine/storage/#storage-mount-options).

## Contract consequences

1. Make `probe(request)` read-only and structured. It must cover host/runtime identity, driver/API versions, health, each requested mount/channel/network/workload-engine feature, and actionable unsupported/degraded reasons.
2. Let `auto` compare these reports only after applying explicit CLI, Workspace, then user-global preference. A preferred driver that cannot satisfy required capabilities returns a normalized incompatibility; it must not silently degrade to a lowest common denominator.
3. Use driver-owned opaque resource IDs plus ownership metadata. Reconcile actual resources before create/start/attach/stop/destroy and after partial errors.
4. Normalize errors by operation and category—unsupported capability, incompatible host/runtime, unavailable runtime, not found, invalid state, conflict, permission, timeout, backend failure, and cleanup incomplete—while retaining redacted backend diagnostics.
5. State cleanup guarantees per resource class. Successful destroy means verified removal of every owned runtime resource in declared scope; otherwise return cleanup-incomplete with residual identifiers and a safe retry path.

## Research boundary

These sources establish observable capability and lifecycle constraints only. They do not prove feasibility, security, or performance of any candidate macOS isolation mechanism, and they do not select how an internal Docker or Podman engine should run. Those questions remain for the separate macOS runtime-isolation research ticket.
